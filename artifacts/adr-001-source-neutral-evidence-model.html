Architecture Decision Record · ADR-001

Use a source-neutral evidence model at the ingestion boundary

Keep source-specific complexity in adapters, and let every downstream capability work from versioned records, traceable claims, and temporal relationships.

Status: ProposedDate: 2026-10-06Scope: ingestion + schemaOwners: Engineering Memory team

Decision

Adopt a technology-independent canonical engineering record and relationship vocabulary as the contract between source adapters and all downstream processing. Adapters translate Git, issue trackers, collaboration tools, review systems and documentation platforms into that contract. Preserve raw source evidence and provenance alongside normalized records. Distinguish explicit facts, deterministic structural extraction and semantic inference. Store event/valid time separately from observation time where the source supports it. Treat graph, search, queue and model technologies as replaceable implementation choices outside the conceptual core.

Context

The product goal is to answer “why is this code like this?” by reconstructing software rationale from code, change history and engineering context. No single source is complete: code reveals current structure; commits reveal change; PRs and issues often explain motivation; discussions capture trade-offs; tests and ADRs constrain interpretation. Source systems have different IDs, schemas, permissions, rate limits and retention rules. Directly coupling the domain model to one vendor would make cross-source relationships, migration and future connectors expensive.

At the same time, an LLM-generated explanation is not evidence. We need an auditable chain from a claim to source locator(s), and the system must be able to report uncertainty or missing rationale.

Problem statement

How should data ingestion represent heterogeneous engineering artifacts so that relationships and history can be queried consistently, without locking the system’s meaning to a particular source platform or storage product?

Decision drivers

  • One stable contract for multiple repositories and external systems.
  • Evidence provenance that survives normalization, extraction, graph loading and answer generation.
  • Temporal queries: what changed, when, who changed it, and what evidence accompanied it.
  • Explicit links must remain distinguishable from inferred links.
  • Incremental ingestion, replay, deduplication and schema evolution.
  • Privacy, permissions and source access scopes must not be lost at the boundary.
  • Prototype feasibility: demonstrate a small end-to-end path before building every connector.

Core record principles

Required concepts

  • Stable canonical ID and source-native identity
  • Record kind, actor, content and context
  • Source reference / locator and checksum
  • Observation time and schema version
  • References, discussion and change envelope

Claim & time semantics

  • Claim status: explicit, extracted, inferred, disputed or unknown
  • Claim method and confidence where applicable
  • Evidence IDs for every derived claim / relationship
  • Valid/event time separate from system observation time
  • Corrections are appended/versioned, never silently erased

Alternatives considered

OptionBenefitsCosts / reason not chosen
Vendor-native model end-to-endFast initial connector; native feature richnessLeaks vendor semantics downstream; multi-source joins and vendor migration become costly
One generic document blobVery flexible and easy to storeWeak typing, validation and temporal/relationship queries; consumers duplicate interpretation
Canonical model with no raw preservationSmaller data footprint and simpler retentionNormalization can discard context; difficult to audit or re-run improved extractors
Canonical records plus raw evidence and typed links (chosen)Portable, auditable, replayable and suitable for temporal graph reasoningRequires schema governance, provenance discipline, access controls and storage lifecycle policies

Consequences

Positive

  • Add sources without changing core consumers.
  • Compare history across systems using common concepts.
  • Explain answers with traceable evidence and visible uncertainty.
  • Replay raw artifacts when parsers or models improve.
  • Swap graph/search/model technology without redefining the domain.

Costs & risks to manage

  • Canonical vocabulary needs versioning and compatibility rules.
  • Source-specific details require extensions; avoid turning extensions into a shadow schema.
  • Raw payloads and Slack-like discussions raise privacy, retention and access-control concerns.
  • Semantic links can be wrong; keep them labeled and thresholded.
  • Backfills, deletion requests and permission changes need explicit lifecycle handling.

Operational rules

  • Every ingestion run records source, cursor range, time, counts, errors and adapter/schema versions.
  • Retries are idempotent; malformed records are quarantined with an actionable error and replay path.
  • Raw and normalized artifacts carry source access labels; authorization is checked at retrieval, not just ingestion.
  • Deterministic IDs use stable source identity; cross-source identity resolution is a separate, auditable relation.
  • Semantic relationships are candidate evidence until a policy or human review promotes them; promotion history is retained.
  • Search/vector indexes are derived views and can be rebuilt from canonical records and raw evidence.

Prototype scope implied by this ADR

First specify and validate the canonical Record, Change, Actor, Decision/Claim and Relationship forms. Ingest a bounded Git history sample and curated linked issue/discussion records. Implement deterministic IDs, paths, timestamps and explicit references before semantic extraction. Load a timestamped relationship graph and demonstrate one question whose answer cites source evidence. Keep Jira and Slack adapters as interfaces/examples until the end-to-end vertical slice works.

Review triggers

  • A source cannot map to the canonical contract without repeated loss of essential semantics.
  • Temporal or access-control requirements cannot be represented safely in the record envelope.
  • Schema evolution causes adapters and consumers to become tightly coordinated.
  • Operational volume or deletion obligations require changing raw-evidence storage or graph materialization strategy.
